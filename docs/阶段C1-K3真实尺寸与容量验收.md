# C1 · K3 真实尺寸与单盘容量验收

在 8 GiB 客体和 3 GiB FEMU BlackBox namespace 上通过两项验收。第一项验证真实尺寸写出与恢复的正确性，第二项验证八个逻辑 rank 在同一条在线调度时间线上向同一块盘提交实际存储请求。[原始证据、配置预算与校验和](../evidence/ssd-c1/)

## 受控恢复

位置 1,536 的 checkpoint 有 12 个共享 MLA chunk 和 24 个 KDA 分片，唯一内容合计 470,605,824 字节。只写 rank 0、以及只缺最后一个 KDA 分片，两次原生 lookup 均返回 0；补齐且驱逐内存副本后返回 1,536。135 次 Store GET 均查到仅有磁盘副本，逐对象摘要和逐层内容检查通过。完整八 rank 恢复阶段读回 619,241,472 个对象字节，同期 FEMU 完成 182 笔读、919,192 个扇区。共享 MLA 在多个 rank 读回，文件页缓存仍能在恢复过程中复用；这两种字节数按各自所在层统计。探针顺序使用八个 rank 的真实布局并复用一套缓冲。[探针账本](../evidence/ssd-c1/probe.json)

## 真实 WEKA 在线准入

前一基线的首轮有 71,175 个输入 tokens；按八份 MLA 副本计算，仅这些 token 的 MLA 有效状态就需要约 7.33 GiB。为保留真实每层尺寸，改用同一公开来源的 trace_0504。检查了该固定版本中按文件大小排序的前 40 份候选，选择 trace_0504 的前两次连续父请求，两次输入/输出分别为 11,133/139 和 11,300/96。保留 64-token WEKA 哈希和原始 4 秒 think time；第三轮有 3,058 秒 think time，未纳入此切片。[原始会话](../references/kimi-k3-b300/trace_0504.source.json) · [选择凭证](../datasets/k3-c2/selection.json)

原生 scheduler 管理同一批块和 Store 任务，八个逻辑 worker 使用独立的 CPU KV 池和原生发送线程。worker 各自消费同一调度决策，原生保存任务按八份完成回执释放块。24 层 MLA 共享一个逻辑分片，69 层 KDA 分为三个 23 层组，各组按八个不同分片存取。一个嵌入式 Mooncake 客户端、一套 TCP 传输端及同一 ext4 目录服务八个 worker。未模拟八张 GPU、八客户端间网络竞争或 B300 forward；数据内容按前缀、层、分片生成占位，传输保留真实页宽、长度和原生分片键。

- 校准运行写出 88 × 1,769,472 字节的 MLA 对象和 120 × 18,723,840 字节的 KDA 对象，208 个唯一键合计 2,402,574,336 字节。5 个导出的 KDA 边界均有完整的 3 × 8 分片。每键记录发起 rank、实际字节和 SHA256；全部写入成功，收尾逐键确认磁盘副本。
- 首轮实际调度产生的位置 2,944、6,016、9,088、11,008 均有内部 checkpoint 记录。导出边界按键的前缀摘要另计。逐 token 重新核对原始 HTTP 载荷，两轮按 WEKA 的 64-token 单位共享 11,072 个 tokens；原生 KV 管理块为 1,536 tokens。第二轮命中 11,008 个本地 tokens，重算 292 个输入 tokens，Store GET 为零。设备读的正例来自上面的受控恢复。
- 采样和实际 HTTP 边界分别保存。第二轮发出前的设备采样显示有 22 笔在途，在读设备计数到实际发送之间完成了一笔 8,192 扇区的写。验收器用独立设备计数核对采样窗口，再显式列出这段差额并还原实际 HTTP 窗口。[逐窗口及对象结果](../evidence/ssd-c1/online.json)

## 本机容量（校准实测）

| 项 | 配置和实测 |
|---|---|
| FEMU 与客体 | 2 vCPU、TCG、8 GiB RAM；单盘暴露 3 GiB，原始 NAND 几何 4 GiB；4 KiB 页，页读/写 40/200 µs。新建 ext4。FEMU 报告宿主 memlock 限制，设备时序可有抖动。 |
| 原生 KV 池 | 每 rank 22 块 × 21,233,664 字节，共预留 467,140,608 字节/rank。计算 step 观测峰值为 18 块/rank，包含 null 块。八 rank 在同一进程使用八套真实尺寸页。 |
| Store 内存段 | 768 MiB 预跑出现原生 PUT 空间不足（返回 -200）。正式配置 2,520 MiB，校准运行中每秒采样的 master 已分配量最高 2,196,612,096 字节。 |
| 传输及 offload 缓冲 | 两个配置预算各 96 MiB；原生客户端内部两个分配器的瞬时用量没有分别导出。并发 PUT 调用中的对象有效字节峰值为 452,911,104；统计从批次进入传输到返回，多个批次可并发。 |
| 其他内存 | 请求摘要峰值 33,914,496 字节；服务进程最高 RSS 为 6,800,105,472 字节；约每秒采样的客体最低可用内存为 845,967,360 字节。RSS、Store 段、KV 池存在包含关系。 |
| 盘容量 | offload 配额 2,840 MiB；文件系统已用量采样峰值 2,403,528,704 字节，含元数据。[配置与准入账本](../evidence/ssd-c1/preflight.json) |

## 复核与重跑

在项目根目录创建独立目录解包。分析使用项目自带 tokenizer 和固定的 K3 几何。

```bash
(cd evidence/ssd-c1 && sha256sum -c SHA256SUMS)
d=$(mktemp -d)
tar -xzf evidence/ssd-c1/femu-c1-probe01.tar.gz -C "$d"
tar -xzf evidence/ssd-c1/femu-c1-online01.tar.gz -C "$d"
.venv/bin/python scripts/check_k3_shard_evidence.py "$d/femu-c1-probe01/probe"
.venv-aiperf/bin/python scripts/analyze_k3_ssd.py "$d/femu-c1-online01" --output "$d/result"
cmp "$d/result/summary.json" evidence/ssd-c1/online.json
```

重做探针和在线校准需使用新的 trial 名。

```bash
.venv/bin/python scripts/run_femu.py --workload k3-probe --trial femu-c1-probe-repeat \
  --guest-ram-mib 8192 --namespace-mib 3072 --blocks-per-plane 2048
.venv/bin/python scripts/run_k3_ssd.py c1 --trial femu-c1-online-repeat
```
