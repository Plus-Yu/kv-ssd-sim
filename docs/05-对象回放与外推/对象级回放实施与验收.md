# n15 上的 K3 对象级回放实施与验收

本文保留首次对象回放的实施记录和当时的对账结果。当前默认回放器已把内存分配、租约、落盘回执与内存淘汰交给 n15 同版本 Mooncake master。新版的构建、逐键验收及仍存在的层级偏差见[原生淘汰实施报告](对象回放器-Mooncake原生淘汰.md)。

2026-11-23，在 `/home/yzh/projects/kv-ssd-sim` 实施。研究量是给定会话历史、缓存容量和到达节奏时，一块 SSD 上方的对象写入与恢复需求。**目前可以复现请求、对象键、分片和恢复字节。容量压力下，哪些恢复会落到磁盘仍有实测反例。** 设备收到的扇区、块大小、峰值带宽、WAF 和 GC 仍由原有 FEMU 闭环测量。

## 实施记录

| 步骤 | 在 n15 上实际做的工作 | 验收依据 |
|---|---|---|
| 1．编译会话 | 调用锁定的 AIPerf 0.13.0 `CustomDatasetComposer`，使用 WEKA 的 coding 语料和随机种子 42。用 chat endpoint 组装原生 turn 中的消息，再用在线服务的 tokenizer 和模板得到 token ID。WEKA 的消息增量已经包含历史回答，遇到上下文重置时从该轮重建。 | 每轮核对源索引、输入和输出长度、token SHA-256。旧离线审计保持原路径。首版直接构造生成器时出现语料差异，逐条 HTTP 摘要检查检出了这个问题。 |
| 2．恢复依赖 | 保存原始 trace ID、会话 ID、父子及跨链前驱、源时间、think time。虚拟时钟释放到达，原生调度器在 step 边界接纳请求。并发计算按该 step 中最大的 prefill/decode 预算推进，输出固定使用项目原有的合成 token。 | 两个并列子任务在示例中同为 0.045 秒到达，父任务等两个子链完成。完整 `0504` 保留第三轮的 3,058 秒等待。重复 trace ID、丢失前驱、长度超限、未支持的分支模式及未完成请求均报错。 |
| 3．推演对象 | 两种运行路径共用 vLLM 配置和固定 K3 几何。使用原生 Scheduler、KVCacheManager、MooncakeStoreConnector 的 lookup、send、recv 和每组 Store layout。八个逻辑 rank 登记具有真实形状和步幅的 PyTorch meta 张量，在 Store API 边界读取 key 和每段长度。 | 原生逻辑决定 MLA 的共享键、KDA 的 rank 分片及块边界。写任务等待计算结束，按 rank 排队，全部八份 job 回执进入下一次调度。异步读等待最慢 rank，覆盖了跨多次空调度仍能收到恢复回执的回归用例。 |
| 4．推演驻留和 I/O | 每客户端分别维护内存段、staging 和 offload 配额。写入者拥有对象，成功 PUT 后即在内存可见，经过后台等待及写队列后才发布磁盘副本。一个共享 FIFO 磁盘服务所有客户端的读写。读优先选内存，活动读与租约会限制回收。 | 记录 PUT、GET、层级、淘汰、失败、写提交和发布的不同时间。读写计算使用完整对象有效载荷。重复读同一 MLA 键的多个 rank 分别记账。 |
| 5．校验和冻结 | 小容量对既有 n15 线上日志，缺片对 C1 的真实尺寸恢复探针，再做独立原生 HTTP 和 Mooncake 宿主文件实验。每次在线启动之前写出五个预测文件的 SHA-256。校验器只读取预测和已结束的实测，不向预测器提供实测的键、命中或副本表。 | 对比单位为请求、rank、完整 key、字节数及出现次数，另查最终盘副本。成功 GET 检查原生恢复的内容摘要。对照曾暴露末轮后台 PUT 失败而服务摘要仍显示通过，已在原生关闭和验收入口补查延迟到达的错误。 |
| 6．参考容量试跑 | 用参考预算同时回放完整 `0504` 和依赖闭合的 `0001` 前两轮。保留每个对象的真实尺寸，八个虚拟客户端共用一块虚拟盘。 | 保留每客户端高水位、每轮 token 和对象账本，并另测宿主峰值 RSS。详见下表及证据目录。 |

短等待与长空闲的四个 HTTP 输入摘要、对象集合和 GET 多重集完全一致。只把最后一轮合成源的 `think_time` 从 7 秒改为 35 秒，同时将该轮源起点从 17 秒平移到 45 秒。实测该轮发送时刻从试验开始后的 11.21 秒变为 35.88 秒，后台回收多出约 25 秒。两组都保留原生内存及磁盘状态，没有人工移除副本。这个配对说明，预测自然回读需要重现候选对象和回收时机，仅对齐总容量和总 GET 字节会得出错误的盘读结论。

原 n15 实物对象的键、大小、内容摘要组合得到 `173bfdbe0ff676b4301cee05be60c30795a68772776cbd8565773d966fda0999`。这是从在线 PUT 重新计算的对照值。元数据回放独立比较完整键和大小。原始输入、原生观测和校验程序均有归档。[n15 基线归档](../../evidence/n15-kvm-20261120-074735/) · [C1 真实尺寸缺片及恢复记录](../../evidence/ssd-c1/) · [本次完整对账和失败记录](../../evidence/object-replay-n15-20261123/)

**对账口径。** 原生 `store_get_begin` 在读之前查询副本目录。“磁盘独存”表示该键只有本地盘副本。“有内存副本”表示这一读可由 RAM 满足。宿主文件实验没有采集块设备读写，这些数值均为对象有效载荷。同一键可供多个 rank 恢复，唯一对象字节和按 rank 累加的读字节有不同分母。

初版只在内存段装满时按字节回收。n15 master 日志在占用率 0.909235 时已经启动回收，因此补入 master 的默认高水位 0.90 和回收比例 0.05。模型在状态变化时按字节回收最久未访问且可回收的对象，原生 master 异步选择候选并受实际分配器、键状态和租约影响。上述 195 对 197 是加入水位后的结果。没有用基线的被淘汰键表回填回放器。

早期竞争组还保留了两类失败。1,100 MiB 段、零租约时，原生在竞争写入中出现 `-200`。1,550 和 2,304 MiB 段、零租约时，真实 master/客户端记录 `lease_expired_before_data_transfer_completed`，GET 返回 `-707`。5,000 ms 是随后单列的实验干预，两端使用相同的租约值。当前服务时间模型给出顺利完成传输时的对象需求，尚未复现原生的分配失败率或传输超时率。

## 证据与字段

每个预测目录含 `launch.json`（容量、版本、源文件及输入哈希）、`requests.json`（因果时间、输入摘要、各层 token、逐轮流量）、`events.jsonl`（lookup、保存回执、读写与发布）、`objects.json`（唯一键、大小及结束时驻留）、`reuse.jsonl` 和 `summary.json`。复用距离只统计可见的 Store 操作。对上一次访问来自另一请求的键，给出时间间隔和其间访问过的其他不同键的有效字节数。纯本地命中出现在请求账本，读取同一 MLA 键的多个 rank 仍保留在事件账本。

合成会话的发出规则取所有前驱满足且原始等待结束的最早时刻。独立宿主实验将已编译的 token 还原为文本后发给原生 HTTP 服务，逐请求核对接收侧摘要。它验证相同输入下的原生缓存行为。AIPerf 多分支 credit 发放器的墙钟开销、GPU step profile、八个真实客户端的并发补写及驱动器服务时间还需要各自测量。

原始证据保存在 [本轮证据目录](../../evidence/object-replay-n15-20261123/)。`inputs.tar.gz` 保存编译输入，`predictions.tar.gz` 保存预测账本，`native.tar.gz` 保存原生服务器的事件、配置、错误、客户端时序和事前冻结哈希，`sources.tar.gz` 保存本轮实现所用的项目源文件。稳定的归档内部路径由 [试验索引](../../evidence/object-replay-n15-20261123/runs.json) 列出。对账 JSON 的 differences 字段逐项列出预测侧和原生侧独有的请求、rank、键和层级。[短等待差异](../../evidence/object-replay-n15-20261123/checks/unseen.json) · [长空闲差异](../../evidence/object-replay-n15-20261123/checks/long-idle.json)
