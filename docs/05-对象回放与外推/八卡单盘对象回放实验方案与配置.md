# 八卡单盘对象回放实验方案与配置

**把一组真实 agent 会话交给一台八卡 Kimi K3 服务器后，哪些 KV 缓存对象会写入 SSD，哪些旧对象会被读回，这些读写在什么时候发生、每次有多大？** 下文记录 n15 上 `aa6cd65` 的容量、选窗和已冻结的 `simulate --profile reference` 对照。省略 `--profile` 会选中容量较小的 `n15` 配置。[容量配置](../../configs/profiles/reference.json) · [回放器与设备仿真的分工图](对象回放器-FEMU-真实服务器差距说明.md)

**研究 Decode 保存、长上下文时钟、调度和带宽时，使用 `--profile reference-context`。** 它沿用下文相同的八卡容量和 136 请求输入，让固定版本的 vLLM 应用正常的 KDA 检查点保留规则。关闭和开启 Decode 保存的全窗写入分别为 111.096 GB 和 264.467 GB。新指南给出这两个数字与历史 235.572 GB 的逐因素对照。[八卡调度时钟、带宽与 12 组验收结果](八卡调度时钟与带宽对照.md)

## 1．一台服务器怎样配置

八张卡共同运行**一个**模型实例。每张卡负责模型的一部分，称为一个 rank。表中 GB、TB 按十进制计算，MiB、GiB 按二进制计算。KV 是模型处理过一段文本后留下的中间状态，相同前缀回来时可以复用。

| 部分 | 主实验取值 | 它怎样影响 SSD 收到的流量 |
|---|---|---|
| 模型与调度 | Kimi K3，8 卡张量并行（TP8）。单次输入加输出最多 **1,048,576 token**。开启前缀缓存和分块预填充，每步最多同时调度 8 条序列、处理 4,096 个 token | 同机的会话共享缓存。即使某次请求有几十万 token，也会分许多步处理，逐步产生可保存的对象 |
| GPU 本地 KV 池（HBM） | 每卡预算 **55 GiB**，八卡约 **440 GiB**。按固定布局每卡有 **2,781 个管理块**，每块 21,233,664 B，覆盖 1,536 token | 返回请求先复用本地前缀。命中得越多，需要向下层恢复的内容就越少 |
| 主存 KV 池（DRAM） | **8 个 Mooncake 存储客户端，各 128 GB，共 1.024 TB**。普通读租约 10 秒，内存回收高水位 90%，回收比例参数 5% | 本地缺的对象仍可从主存取回。由同版本 Mooncake 原生 master 根据占用、租约、可用副本等状态挑选回收对象 |
| SSD 容量 | **一块 30.72 TB 逻辑 SSD**。其中给 KV **24 TB**，每个存储客户端独立使用 **3 TB** | 30.72 TB 来自八块 3.84 TB 缓存盘的标称容量之和。单个客户端超过自身 2.7 TB，才按文件桶回收到不高于 2.4 TB。各客户端的占用可以不均匀 |
| SSD 队列与带宽 | **一条读写共用的先进先出队列**。默认读 **6.8 GB/s**、写 **5.0 GB/s**，场景名 `1x` | 一个桶开始服务后，后面的读写都要等。主实验输出整机汇入这个逻辑设备的需求，账本保留每个对象的文件所有者 |
| 从 SSD 恢复的资源 | 每个文件所有者有 **4 GiB** 主机暂存，每个目标 rank 有一个主机到 GPU 的复制端口 | 先在所有者处留空间、排队读盘，再向需要对象的卡复制。暂存占满，后来读同一客户端文件的请求就要等 |

55 GiB/卡和 1M 上限参考公开的单机 B300 部署。DGX B300 官方规格提供整机缓存盘的容量依据。1.024 TB 主存、24 TB KV 配额、同机路由、一条设备队列都是本项目选择的实验条件。单盘服务率采用 Micron 7450 PRO E1.S 顺序读写的参考值。每块物理盘的流量分布、并行度和随机访问延迟仍需单独测量。[AWS 单机 K3 部署记录](https://github.com/aws-samples/sample-llm-inference-on-eks/blob/main/docs/KIMI-K3-B300-PERFORMANCE.md) · [NVIDIA DGX B300 规格](https://docs.nvidia.com/dgx/dgxb300-user-guide/introduction-to-dgxb300.html) · [盘型、容量与模型假设](../../configs/profiles/reference.json) · [K3 缓存布局](../../configs/kimi-k3-b300-step2/resolved.json)

## 2．跟着一次会话，看对象什么时候上盘

~~~mermaid
flowchart TD
    A["旧会话回来"] --> B{"GPU 本地有可复用前缀？"}
    B -->|命中的部分| C["直接复用"]
    B -->|缺的部分| D{"Mooncake 可恢复哪份副本？"}
    D -->|内存副本| E["从主存复制到目标 rank"]
    D -->|只有已发布的磁盘副本| F["在文件所有者处预留暂存，排队读 SSD"]
    F --> E
    E --> G["所需 rank 全部完成，请求继续"]
    D -->|缺少完整可恢复前缀| H["重新计算未覆盖的 token"]
    H --> I["保存新增 KV 到 Mooncake 主存"]
    I --> J["后台将待写对象分桶，排队写 SSD"]
    J --> K["写完并发布，后续请求可以从盘恢复"]
~~~

**先看写。** 客户端可以把多个待写对象装进同一个文件桶，作为一笔写提交。保存一次 KV（PUT）、后台提交桶写、文件写完并发布，是三个时刻。后台会主动落盘，即使主存还有空位也可以写。八个客户端的首次轮询相位均为 0，各自处理完一轮工作再等 10 秒。较慢的写会推迟该客户端的下次轮询，下一轮能合在一个桶里的对象也可能改变。[后台策略、租约和盘水位](../../configs/storage/mooncake-single-volume.json)

**再看读。** 回访旧会话时，本地或主存仍有可复用内容，就能省掉相应的 SSD 读。只有已发布的文件副本可用时，才发生这里统计的「自然回读」。从 SSD 读完后，数据还在主机暂存区，等复制到目标卡才可释放这份暂存。一个需要多卡恢复的请求，要等所需子批和 rank 都完成才能继续。这段等待也会影响依赖该请求的下一轮何时到达。[两阶段恢复的实现与验收](大容量单盘与两阶段KV恢复验收.md)

**八卡会产生多少份数据？** K3 的两类缓存有不同的共享方式。以保存一个完整的 1,536-token 检查点为例，MLA 每 128 token 有一个 1,769,472 B 的共享键，合计 12 个。KDA 有 3 组状态，每组按 8 个 rank 分片，合计 24 个不同的键，每个 18,723,840 B。这样一共是 **36 个唯一对象、470,605,824 B**。恢复时多个 rank 可以分别读取同一个 MLA 键，因此要分别数「唯一对象」和「实际读取次数」。[真实尺寸与逐 rank 检查点探针](对象级回放实施与验收.md)

## 3．请求从哪里来，时间怎样走

**输入。** 采用 WEKA kvlab 的 `replay-v5`。2026-09-05 至 2026-10-14 的语料共 **3,190 个会话、370,658 个请求**。记录自带 UTC 时间、持续时间、前后轮与子任务依赖、可用的 token 长度和脱敏内容指纹。编译器用相同的角色和指纹重建可识别的共享前缀，用合成 token 填充，无法辨认的尾部按请求隔离。保留每次实际记录的输出长度，K3 的命中由本次回放重新决定。[WEKA 回放格式](https://github.com/weka/kvlab/blob/main/docs/replay.md) · [固定数据版本与摘要](../../evidence/kvlab-first-windows-20261124/provenance.json) · [前缀重建实例](kvlab首轮窗口与SSD对象负载验收.md)

**并发与前史。** 根请求保留彼此的源到达时间差。普通后继等待目标端前序完成，再加原记录的间隔。如果源记录中后继请求在前序尚未完成时已启动，就以目标端前序开始时刻加原有偏移释放。选中的会话全部路由到同一服务器。同一窗口的 7 个会话随时间进入和离开，实际并发度逐时变化。1M 上限下，325,751 个请求自身长度可用，其中 **241,219 个连同所需前序都可用**，覆盖 **1,787 个完整会话、全库 66.24% 的已记录输入 token**。把失去父请求的单轮接到空缓存上，会改写它原本可能发生的复用。[全库覆盖审计](../../evidence/tp8-public-20261125/audit.json) · [1M 与 128K 的覆盖对照](单机八卡公开参考配置与上下文覆盖.md)

**本次正式窗口。** 选取依赖完整、含会话交错后返回的最长连续候选。源时间为 **2026-09-06 04:37:20 至 05:00:27 UTC**，约 23 分钟，共 **7 个会话、136 个请求**。源端记录给出「此时没有请求在途」的起点，实验在这里把缓存初始化为空。按源顺序取前 32 个请求预热，第 33 个作为开始测量的标记。全程保留 GPU 池、Store、副本、租约和 SSD 队列。1× 下，这个请求在虚拟时间 **320.756269648 秒**被接纳，此前目标端已接纳 35 个、完成 34 个请求。这是并发与因果时钟共同产生的顺序。[源窗口与编译输入摘要](../../evidence/tp8-logical-volume-20261125/warm-window.json) · [实际测量边界](../../evidence/large-ssd-staged-20261125/warm-comparison.json)

| 哪一段时间 | 主实验怎样推进 | 取值依据 |
|---|---|---|
| K3 前向计算 | CPU 版 vLLM 实际调度，跳过 GPU forward。全机预填充按 **22,000 个新 token/s**，解码每步从 batch 1 的 **11.77 ms** 到 batch 8 的 **14.10 ms** 线性插值。含新 token 的一步取预填充时间与对应解码时间的较大值 | 预填充借用 B300 上另一推理引擎的测量，解码借用八卡 GB300 的特定上下文测量。均为虚拟时钟输入 |
| GPU ↔ 主机复制 | 新保存的有效字节按每 rank **57.3 GB/s** 从 GPU 复制到主存。恢复到目标 rank 按 **55.7 GB/s**。固定分配与保存控制耗时设为 **0 ms**，数据复制仍消耗时间 | 借用公开的大块主机拷贝测量。内存 GET 和盘读后的复制竞争同一个目标端口 |
| 逻辑 SSD | 写入服务时间为桶字节数除以写带宽，读取按读带宽换算。提交后要等前一笔完成才开始服务 | 单队列支持观察提交突发、排队和排空。真实设备的块拆分、闪存并行、擦除由设备实验测量 |

例如某一步新处理 2,200 个 token，主配置预留约 100 ms，这段时间里已经提交的后台桶写也能推进。哪一份副本赶在下一次 GET 之前就绪，由这些事件的先后决定。画负载曲线时用这条虚拟时间轴。n15 实际运行程序所耗的墙钟时间反映宿主执行回放的速度。[计算与复制参数的原始测量链接](../../configs/hardware/b300-tp8.json) · [步耗时公式](../../src/kv_ssd_sim/simulation/timing.py) · [单队列实现](../../src/kv_ssd_sim/simulation/storage/device.py)
