## 1M 上限的来源与 131,072 对照组

**1,048,576（2²⁰）来自 Moonshot 发布的 Kimi K3 文本模型配置**，字段为 `text_config.max_position_embeddings`。项目锁定的模型 revision 为 `f831ab66814297da540d832a5235f8e904f29d06`，对应 vLLM 部署配方也列出了 `context_length: 1048576`。AWS 在单机八卡 B300 上用 `--max-model-len 1048576` 启动 K3 TP8，记录了该设置下的 KV 池分配。[Moonshot 官方模型配置](https://huggingface.co/moonshotai/Kimi-K3/blob/main/config.json) · [项目锁定的模型原件](../../references/kimi-k3-b300/model-config.json) · [固定版本与校验和](../../references/kimi-k3-b300/sources.json) · [vLLM 配方副本](../../references/kimi-k3-b300/recipe.yaml) · [AWS 实测第 1–2 节](https://github.com/aws-samples/sample-llm-inference-on-eks/blob/main/docs/KIMI-K3-B300-PERFORMANCE.md)

**131,072 是首轮实验主动设置的单请求上限。** 项目从部署配方下调该值，固定调度条件做基线，并关闭输入和输出截断。本轮容量、租约与节奏的对照沿用了同一批窗口。单个会话可以跨多轮，累计处理超过上限的 token，各轮之间的缓存由实际容量和淘汰规则管理。[首轮配置及覆盖说明](../../configs/kimi-k3-b300-reference.json) · [本轮基准启动清单](../../evidence/tp8-public-20261125/base-launch.json)

例如，第一轮需要 180,000 token，工具返回后的第二轮只需 90,000 token。第二轮本身进得去 131,072 的实例，但第一轮无法按原样执行。若直接从第二轮冷启动，就丢掉了第一轮留下的本地块、Store 副本、盘上对象和仍在排队的写。旧前缀可能变成重算，也可能漏掉本来会发生的 SSD 读。选窗因此沿 WEKA 的 `prev` 和 `spawn` 一直检查到会话根。缺长度、超上限或依赖无效的请求，会使依赖它的后续轮次失去资格。选中的连续时间段还包含中间到达的竞争会话。窗口左边界取源端 API 空闲点，并假设实例冷启动；更早已结束会话留下的全盘缓存状态仍然未知。[WEKA 格式](https://github.com/weka/kvlab/blob/main/docs/replay.md) · [依赖与选窗代码](../../src/kv_ssd_sim/workload/windows.py)

按锁定的 40 天原文件校验 SHA-256，共有 3,190 个会话和 370,658 个请求。对审计索引的 `calls` 表筛选 `n_in > 0 AND n_out > 0`，实录单请求最大值为 **1,012,441 token**（999,098 输入 + 13,343 输出）。下表覆盖率的分母是全库记录到的 **91,591,785,836 个输入 token**。“完整会话”要求整个会话的每个请求都合格，单个合格请求只要求自己的祖先链完整。[全库审计与输入摘要](../../evidence/tp8-public-20261125/audit.json) · [审计索引生成代码](../../src/kv_ssd_sim/workload/corpus.py)

| 单请求上限 | 自身长度合格 | 前序也全部合格 | 合格部分输入 token | 占全库输入 | 完整会话 |
|---|---:|---:|---:|---:|---:|
| 131,072 | 66,478 | 30,760 | 2,589,159,147 | 2.83% | 680 |
| 1,048,576 | 325,751 | 241,219 | 60,668,778,793 | 66.24% | 1,787 |

131,072 下，有 **35,718** 个自身能放入的请求因前序不完整被排除。1,048,576 下，数据中已有输入、输出长度的请求全部放得下。仍有 **44,907** 个请求缺少有效长度，另有 **84,532** 个自身合格的请求受前序影响。因此，研究长期 agent 负载时，应以 **1,048,576 且前序完整**的样本为主，另报 131,072 对照组。66.24% 表示源输入覆盖率，实际打到单块 SSD 的流量还取决于会话路由、驻留和节奏。[旧版覆盖审计](../../evidence/kvlab-first-windows-20261124/audit.json) · [新版覆盖审计](../../evidence/tp8-public-20261125/audit.json)

## 在 n15 验证了什么

以下读写字节按回放中提交给文件后端的对象载荷统计。同一键被多个 rank 恢复时分别计量，窗口覆盖首次到达至最后一个后台事件之后的首个维护边界。块地址、主机块读写、NAND 编程和 GC 由独立的 FEMU 设备实验观测。n15 已归档的设备基线是 48 MiB 校准探针与 3 GiB 的 `0504` 两轮回放。[逐场景对账和逐键读事件](../../evidence/tp8-public-20261125/verification.json) · [运行时清单](../../evidence/tp8-public-20261125/base-launch.json) · [FEMU 设备基线](../04-n15迁移与容量验收/n15-KVM基线与56GiB容量验收.md)

| 负载 | 单请求上限 | 请求 | 唯一键 | 文件读次数 | 文件读字节 | 文件写字节 | 最后一个请求结束后提交的写字节 |
|---|---:|---:|---:|---:|---:|---:|---:|
| kvlab A，八卡参考容量 | 131,072 | 3 | 1,970 | 0 | 0 | 20,575,862,784 | 2,434,424,832 |
| kvlab B，八卡参考容量 | 131,072 | 3 | 2,462 | 0 | 0 | 25,515,491,328 | 0 |
| kvlab B，相同请求、放宽上限 | 1,048,576 | 3 | 2,462 | 0 | 0 | 25,515,491,328 | 0 |
| 35 秒返回，历史小容量配合新时钟 | 12,288 | 4 | 108 | 24 | 42,467,328 | 1,411,817,472 | 0 |
| 长请求，334,097 输入 + 539 输出 | 1,048,576 | 1 | 5,226 | 0 | 0 | 53,599,887,360 | 18,679,283,712 |

两个 kvlab 窗口都保留了另一个会话的插入和随后返回的请求。返回时分别本地复用了 73,728 和 3,072 个 token。两个窗口均未发起 Store GET。35 秒压力用例则沿用 1 个 Store 客户端、11 块/rank、1,450 MiB 内存段和 2,840 MiB 配额，使用同一套公开时钟及租约。在记录中，先有文件发布，再有原生内存淘汰，随后 120 次 Store GET 中 **96 次走内存、24 次走盘**。24 次磁盘 GET 涉及 **3 个不同的键**。逐次核对了请求、rank、任务、键、大小、读提交、读完成和 GET 完成。它检验了模型的回读路径；目标机逐键自然回读的准确率仍需用独立原生文件读记录测量。[压力回放和两个参考窗口的原始事件](../../evidence/tp8-public-20261125/runs.tar.gz)

两个参考窗口各运行了五个场景。只把计算时间减半或加倍，或者只把 SSD 服务速率降至规格的 1/2、1/4。两个窗口内对象读写总量各自相同，写入的时刻发生了变化。例如 B 窗口在基准设置下，请求结束时所有写已经提交。单盘带宽降到 1/4 时，**14,563,215,360 B** 在最后一个请求结束后才提交。即便短窗读写总量相同，后台排空和突发带宽的结论也要注明采用的节奏。[五个场景的结果](../../evidence/tp8-public-20261125/verification.json)

1M 选窗采用相同的源端排序规则，自动选出的 A、B 都能放进 131,072。B 窗口两次编译得到的三条请求逐项相同，输入文件中的 `context_limit` 字段记录各自的上限。为验证长请求，从 API 空闲边界、依赖完整、300 秒内的单请求窗口中，另取源时间最早且超过旧上限的一条。它包含 334,097 输入 token 和 539 输出 token，已在 1M 上限下完整跑通。这是单请求容量验证。40 天全库本轮完成的是覆盖审计。[超旧上限的源窗口](../../evidence/tp8-public-20261125/over-128k-window.json) · [测试记录](../../evidence/tp8-public-20261125/tests.log)

可在审计生成的 `$work/corpus/index.sqlite` 上复核实录最长请求。该查询按单次请求的输入加输出排序，返回 999,098、13,343 和 1,012,441 三个值。

```sql
SELECT n_in, n_out, n_in + n_out AS total_tokens
FROM calls
WHERE n_in > 0 AND n_out > 0
ORDER BY total_tokens DESC
LIMIT 1;
```
