# 八卡服务器的计算时钟、Decode 保存与带宽对照

2026-11-26，n15。研究同一批 agent 请求进入一台 Kimi K3 八卡服务器后，改变软件策略或硬件服务速度，会怎样改变 SSD 的对象读写。在同一份 136 请求窗口中，**开启 Decode KV 保存使写入从 111.096 GB 增至 264.467 GB**。增加的字节中 **99.62% 来自 KDA 状态分片**。两组的 SSD 对象读均为 0 B。下文的秒数均指回放虚拟时间，GB 按十进制计算。[12 组逐场景结果](../../evidence/b300-context-20261126/study.json)

## 一台机器，两个可复现入口

现在做这五项实验用 `simulate --profile reference-context`。目标仍是一台 B300、Kimi K3 MXFP4、逻辑 TP8/DCP1/PP1、一个聚合式推理实例。八个 rank 各有 2,781 个本地块，Store 总计 1.024 TB，逻辑 SSD 标称 30.72 TB、KV 配额 24 TB，读写共用一个 FIFO。原生 vLLM 在 CPU 上做调度，八个逻辑 worker 生成真实 K3 缓存键和尺寸。同一窗口内跨请求连续保留缓存，预热与测量边界沿用原方案。[容量、对象布局与选窗](八卡单盘对象回放实验方案与配置.md) · [上下文时钟参数](../../configs/compute/b300-tp8-context.json)

| 本轮关心的因素 | 新研究基线 | 单因素对照 |
|---|---|---|
| SSD 带宽 | 1×，读 6.8 GB/s、写 5 GB/s | 4× 为 27.2 / 20 GB/s，8× 为 54.4 / 40 GB/s。始终一条队列。4× 是假设，8× 是八块参考盘顺序带宽的算术和 |
| GPU 与主存之间的带宽 | D2H 57.3 GB/s/rank，H2D 55.7 GB/s/rank，按源内存端口和目标卡排队 | 一组把两个方向的有效速率同时减半，另一组保留单端口速率，但只允许全机同时有 4 笔复制。PUT 和两类 GET 竞争这 4 个名额 |
| Decode 保存 | 关闭，使用 vLLM 的常规检查点保留设置 | `--save-decode-cache` 开启原生 Connector 策略。两组都允许恢复，保持普通租约、后台分桶与 Mooncake 淘汰相同 |
| GPU 计算 | 预填充和解码都以同一套八卡 B300/vLLM 服务的公开请求延迟为锚点，每一步使用实际调度到的各序列历史长度 | 换回旧混合来源时钟，或只把估算的 MLA 长度开销乘 2，分别判断来自计时依据和长上下文假设的差异 |
| 原生调度 | 最多 8 条序列、每步 4,096 token。开启分块 prefill、前缀缓存和异步加载，使用同步 lookup 和同步调度，关闭推测解码 | 单独把并发上限改为 16、32，或单独把 token 预算改为 2,048、8,192。八卡始终共同服务一个模型 |

历史大盘运行使用 `--profile reference`，省略 Decode 策略选项时沿用原先的密集保留。在这个旧时钟上显式加 `--no-save-decode-cache` 会从正常规划值 0 开始，这就是矩阵里的 `legacy-clock`。读新实验的 `launch.json` 时，`scheduler` 是从已创建的原生调度器回读的参数，`logical_volume` 给出实际盘速。`reference_settings.baseline` 留存基础容量配置及其历史参数。新时钟实际使用的数据和公式系数见 `compute_calibration` 与 `step_timing`。[正式容量配置](../../configs/profiles/reference.json) · [实验矩阵](../../scripts/run_kvlab_matrix.py)

## 为什么一项保存开关会多写 153.370 GB

模型生成的 token 可能成为下一轮的输入。关闭 Decode 保存时，原生 Connector 跳过生成阶段新到达的保存边界。开启后，满足边界的 MLA 块和 KDA 分片可以进入 Store，普通后台流程再决定怎样组桶和写盘。开启该策略还会改变哪些本地 KDA 检查点继续保留，所以必须把选键与保留策略一起交给同一版本的 vLLM。[固定版本的 Connector](https://github.com/vllm-project/vllm/blob/be47189f37f6162991366ff6b91539f6e9d1f432/vllm/distributed/kv_transfer/kv_connector/v1/mooncake_store/scheduler.py)

核对时发现，旧回放器手工创建的 `KVCacheConfig` 采用数据结构默认值 `None`，表示密集保留检查点。真实 vLLM 的规划器会把 `CacheConfig` 中的值传入，默认是 `0`，表示保留语义边界。新入口复现这个传递过程。原生 Connector 在开启 Decode 保存时再把 `0` 调整为 **1,536 token**。每个实验的 `scheduler.prefix_cache_retention_input` 与 `scheduler.prefix_cache_retention_interval` 记录调整前后值。[原生缓存配置](https://github.com/vllm-project/vllm/blob/be47189f37f6162991366ff6b91539f6e9d1f432/vllm/config/cache.py) · [回放器接入](../../src/kv_ssd_sim/simulation/worker.py)

| 相同 136 请求，从首请求到后台排空 | 实际保留间隔 | 唯一写键 | 写入 B |
|---|---:|---:|---:|
| 历史 `reference`，旧时钟、Decode 保存关 | `None` | 19,992 | 235,572,461,568 |
| `legacy-clock`，旧时钟、Decode 保存关，传入正常规划值 | 0 | 13,344 | 111,096,373,248 |
| `base`，上下文时钟、Decode 保存关 | 0 | 13,344 | 111,096,373,248 |
| `save-decode`，上下文时钟、Decode 保存开 | 1,536 | 21,834 | 264,466,833,408 |

前两行隔离了本地检查点保留方式。第二、三行隔离了时钟。最后两行隔离了原生 Decode 保存开关的**整体策略效果**。逐键比对，开启后多写 **330 个 MLA 对象、583,925,760 B**，以及 **8,160 个 KDA 分片、152,786,534,400 B**。关闭时写过的键在开启组里都能找到。一个独立的短探针用 1,520 个输入 token 再生成 160 个，在跨过 1,536 时开启组新增 1 个 MLA 键和 24 个 KDA 分片。kvlab 的生成内容已脱敏，回放使用合成输出 token。这些结果能解释这个窗口的写量，更长会话实际会复用多少生成内容还要用可核对的原生文件读来校准。[逐键差集](../../evidence/b300-context-20261126/study.json) · [边界与原生调度测试](../../tests/test_context_replay.py)

## 怎样把同一部署的数据变成上下文时钟

AWS 在一台 p6-b300.48xlarge 上以 vLLM 运行 Kimi K3 TP8、FP8 KV，报告了同一服务在两种输入长度下的客户端首 token 延迟（TTFT）和相邻输出 token 间隔（ITL）。预填充锚点取单并发、1,024 输入 token 的平均 TTFT **241 ms**。解码使用下表的平均 ITL。两个工作负载均输出 1,024 token，所以用约 **1,536** 和 **8,512** 代表解码过程的平均有效历史长度。源报告说明指标包含启动负载的过渡期，服务并发数也只是实际调度批次的近似。[AWS 测量方法与结果，第 4–5 节](https://github.com/aws-samples/sample-llm-inference-on-eks/blob/main/docs/KIMI-K3-B300-PERFORMANCE.md)

| 输入 / 输出 | 并发 1 | 并发 8 | 并发 16 | 并发 32 |
|---|---:|---:|---:|---:|
| 1,024 / 1,024 的 ITL | 9.45 ms | 14.57 ms | 17.84 ms | 24.12 ms |
| 8,000 / 1,024 的 ITL | 缺测 | 18.1 ms | 22.3 ms | 34.2 ms |

- **Prefill 看新增 token 和已有前缀。** 用 241 ms 约束冷启动的 1,024-token 工作量。同样再处理 512 个 token，前面已有 100,000 个 token 时，MLA 要做更多查询与历史键的乘加。回放按每条序列本步新增数与它所见的历史计算，只对新增部分计费。把同一个长提示切成多块时，前一块形成的历史会计入后一块。
- **Decode 看每条序列各自的长度。** 在有测量的上下文与批次之间插值。短于第一个历史锚点时采用短上下文 ITL。单并发的第二格缺测，以及超过 8,512 的额外长度，使用每 rank 每个历史 token 的 **13,824 B** MLA 读取量估算。混合步取本步预填充与解码估算的较大值。每步的 `context_before_tokens`、`fresh_tokens_by_sequence` 和 `duration_ns` 都可从事件中复算。
- **长上下文属于外推。** 采用 HGX B300 稠密 BF16 规格折算的每 GPU **2.25 PFLOP/s** 和 DGX B300 总 HBM 带宽折算的 **7.75 TB/s/GPU**，估算额外 MLA 工作。这里的 HBM 带宽和 CPU↔GPU 复制带宽是两种硬件资源。`--context-cost-scale 2` 将估计开销加倍，可检查结论对该假设是否敏感。136 请求基线的 78,947 个计算步中，78,908 步至少一条序列超过 8,512 token，最长实际上下文为 202,323 token。这个窗口的绝对时间尤其需要目标机长上下文 step 数据校准。[NVIDIA HGX 算力规格与稀疏脚注](https://www.nvidia.com/en-us/data-center/hgx/) · [DGX B300 HBM 规格](https://resources.nvidia.com/en-us-dgx-software/dgx-b300-datasheet) · [公式与单位换算](../../src/kv_ssd_sim/simulation/timing.py)

如有同一部署的校准数据，用 `--step-profile 文件.json` 提供成对的两阶段参数，沿用配置示例的字段、单位和目标拓扑。启动清单保存完整参数和来源文件 SHA-256。当前 AWS 实验和项目的 vLLM 版本不同，公开证据支持同部署的两阶段参考时钟，精确的逐步 GPU 用时仍待设备采样。[参数文件及来源](../../configs/compute/b300-tp8-context.json)

## 带宽和并发实际上改变了什么

单卡两个方向的速率来自八卡机器上逐 GPU 的 1,024 MB pinned-memory 复制测试。在共享 4 个名额的对照中，4 笔同时从 GPU 写主存的理论上限是 229.2 GB/s，4 笔同时从主存读回 GPU 是 222.8 GB/s。读写混合时，两种方向合计最多 4 笔。SSD 的 1× 取 Micron 7450 PRO 参考规格，4× 和 8× 只改变同一逻辑盘服务一笔 I/O 所需的时间。[B300 主机复制实测 §4c.5](https://github.com/ricardojacomini/b300-benchmarks/blob/main/report/b300_benchmark_report.md) · [单盘服务率依据](../../configs/profiles/reference.json)

| 只改一项 | 136 请求全窗观测 | 可以判断什么 |
|---|---|---|
| SSD 1× / 4× / 8× | 各写 111.096 GB，分别有 824 / 833 / 831 笔桶写 | 设备服务时间改变了下一轮分桶的时机。比较整机需求时保留三档，并在论文中标明所用速率 |
| 主机复制限 4 笔并发，或把双向端口速率减半 | 两组全窗读写总量与基线相同。限 4 笔后，实际复制并发峰值从 8 降至 4，D2H 任务合计多等 0.982 秒。这是各任务排队时间之和 | 控制共享带宽会改变复制时刻。限额按双向合计，模型另计 SSD 服务，PCIe/NUMA 和 SSD DMA 的共享程度仍需实测 |
| 最大序列数 8 / 16 / 32 | 三组实际调度峰值都为 **3**，全窗读写相同。另用 32 个同时到达的短请求验证了原生调度实际达到 batch 32 | 这个真实窗口的瓶颈不在序列上限。32 路短探针验证功能，不能用来代表真实到达率 |
| 每步 token 预算 2,048 / 4,096 / 8,192 | 全窗分别写 **120.533 / 111.096 / 108.850 GB** | 切分同一批提示的方式会改变 KDA 状态写入。这个窗口里，token 预算比序列上限更能改变写量 |
| 时钟与外推假设 | 正常保留设置下，旧时钟、上下文时钟、上下文估计开销加倍的最后响应分别在 **1,401.44 / 1,530.13 / 1,535.90 秒**。三组总写量相同，按 10 秒分箱的最大提交写入量分别为 **4.395 / 3.245 / 2.799 GB** | 时钟会改变 SSD 在一个短窗口内收到多少数据，比较写突发时要附上所用的时钟 |

另用原先 35 秒后返回的自然回读用例单独检查共享复制限制。这两次都保留历史时钟和缓存配置，只改变共享名额。不限时 H2D 最多同时服务 2 个目标 rank，限制全机 1 笔后峰值降到 1。两次均有 **24 次磁盘 GET、42,467,328 B**，最后恢复完成时刻从 **35.115623980 s** 变为 **35.116291108 s**。这次隔离出的机制是盘后复制的排队。以上实验给出对象读写和恢复时序，NAND 编程与 GC 仍由 FEMU 设备实验独立测量。[主存与 SSD 恢复的逐阶段检查](../../src/kv_ssd_sim/analysis/restore.py) · [复核记录](../../evidence/b300-context-20261126/verification.json)

## 在 n15 上复现

下面的 Bash 命令解开同一份冻结输入。只看单个因素，可以在矩阵命令后加入 `--case base --case save-decode` 等选项。完整对账命令读取全部 12 组结果，检查输入身份、实际调度参数、逐步时钟、分桶写入、自然 GET 和主机复制并发。

~~~bash
cd /home/yzh/projects/kv-ssd-sim
source .object-replay-build/trials/kvlab-20261124/env.sh
export KV_SSD_OBJECT_MASTER_DIR="$PWD/.object-replay-build"
export PYTHONHASHSEED=0
work=$(mktemp -d "$PWD/.object-replay-build/trials/b300-study-XXXXXXXX")
mkdir -p "$work/windows/warm"
frozen=evidence/tp8-logical-volume-20261125
xz -dc "$frozen/warm-input.json.xz" > "$work/windows/warm/input.json"
cp "$frozen/warm-window.json" "$work/windows/warm/window.json"
"$py" scripts/run_kvlab_matrix.py "$work/windows" --window warm \
  --profile reference-context --jobs 4 --output "$work/results"
"$py" scripts/compare_deployment_replay.py "$work/results/warm" \
  --window "$work/windows/warm/window.json" > "$work/study.json"
cmp "$work/study.json" evidence/b300-context-20261126/study.json
~~~

单独使用正式对象回放入口也可设置这些参数。例如下面一组允许 16 条序列，打开 Decode 保存，使用一块 4× 服务率的逻辑盘，对两种方向的主机复制合计限 4 笔。它演示参数组合，论文中的因素归因使用上文逐项变化的矩阵。

~~~bash
"$py" -m kv_ssd_sim simulate "$work/windows/warm/input.json" \
  --profile reference-context --save-decode-cache --max-num-seqs 16 \
  --max-num-batched-tokens 4096 --volume-service 4x --host-copy-lanes 4 \
  --output "$work/combined"
~~~

这组组合配置已跑完 136 个请求，全窗提交 264,466,833,408 B 写入、0 B 读取。非集成测试通过 128 项，原生集成测试通过 9 项。历史 136 请求窗口和 35 秒回读用例各有 9 个确定性产物与原运行逐项对上。复核记录包含每组原始输出在 n15 的目录、运行清单和事件文件的 SHA-256。[实际运行与测试记录](../../evidence/b300-context-20261126/verification.json) · [本轮证据校验清单](../../evidence/b300-context-20261126/SHA256SUMS)
