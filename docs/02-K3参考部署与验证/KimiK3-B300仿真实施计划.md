记录日期：2026-11-18。

## 目标与范围

下一交付：**Kimi K3 缓存几何与八卡 B300 容量约束下，真实 WEKA 有界切片驱动的 SSD 存取实验。**

继续采用无 GPU 原型路线：不加载模型权重、不执行真实 forward；计算使用明确记录的固定 step 预算；保留原生 vLLM 调度、缓存块管理、Mooncake 对象组织与存取，以及 FEMU 完成事件反馈。模型与服务器名称本身不会改变仿真行为，必须落实到缓存尺寸、容量、分片、调度和设备配置。

第一版研究文本请求，暂不加入视觉编码、推测解码和跨节点部署。固定计算时间未经目标硬件标定时，结论限定为该计算假设下的存储实验，不预测 B300 的真实吞吐或端到端 TTFT。

## 参考部署与待固定参数

采用八卡 B300 单节点 TP8，硬件规格以 DGX B300 为参考。步骤 1 将模型 revision、软件 commit、部署 recipe 和文件 SHA256 固定到 [参考配置](../../configs/kimi-k3-b300-reference.json) 和 [来源清单](../../references/kimi-k3-b300/sources.json)；步骤 2 的[转换结果](../../configs/kimi-k3-b300-step2/resolved.json) 给出原生缓存映射及实验容量预算。

| 类别 | 参考值 / 选择 | 实施时必须核实 |
|---|---|---|

| 层组成 | 93 层：69 KDA＋24 Gated MLA | 逐层顺序、模型配置到原生缓存 spec 的映射 |

## 当前基础与缺口

原生 vLLM＋Mooncake、tiny MLA/KDA、AIPerf HTTP 接入和实际 FEMU 功能闭环已建立。11 月 17 日的联合实验中，入队前人工清缓存的时间波动抵消了设备读变慢的影响，包含客户端 TTFT 的严格配对失败。该次原始结果见[历史联合验收报告](../01-原型与闭环接入/AIPerf-FEMU联合验收报告.md)。

当前实现仍有以下限制，不能把它直接称为目标服务器仿真：

- 原生运行时为 TP1、PP1、world size 1；最多 8 个活跃请求、每 step 最多 128 tokens，若干参数仍写死。
- tiny 配置只有 1 个 MLA 层和 1 个 KDA 层，MLA 固定 FP16，块与前缀粒度多处固定为 64 tokens。
- CPU KV 池有 1 GiB 保护上限，占位摘要有 512 MiB 上限；现有 FEMU 客体为 4 GiB RAM，设备可见容量 384 MiB。
- 步骤 2 已给出目标服务器的独立容量预算，现有 HTTP 运行时仍按本机小型缓存池派生 Mooncake 容量。
- FEMU 入口可接收有界串行 trace 和运行时支持的混合配置。步骤 3 的 K3 真实尺寸 TP8 分片仍在宿主文件系统上验证。
- 已验证 TP1 小工作集的自然容量淘汰、并发保存、FEMU 读回与缺片重算。长期内存增长、完整真实 trace、并发多卡设备恢复和布局对照尚未验证。
- Mooncake 删除后同键重新落盘问题已定位但未修复，见 [排查报告](../01-原型与闭环接入/Mooncake同键重落盘排查.md)。

容量预警示例：在未做 TP 分片、卷积状态 2 字节、递归状态 FP32 的假设下，K3 每层 KDA 状态约 6.21 MiB。将 69 层和 128 个块直接代入当前原型池分配方式，约需 53.6 GiB。此数值用于说明直接套配置会触发现有资源限制，不是生产 K3 的实际内存测量。

步骤 1 应首先明确一个可在本机资源内执行、依赖完整且有前缀复用的切片，不直接以百万上下文或全量 trace 起步。步骤 3 可先交付代表性 rank 的中间验证，但必须标记为部分范围；整机结论要等全部目标分片的生命周期得到验证。

## 必须保持的实验口径

1. **权重不加载，容量不能忽略。** 每 rank 的 KV 预算由可用显存扣除权重、激活、通信、图捕获和其他运行时开销后确定；MoE 激活参数量不能替代总权重驻留预算。
2. **多卡按实际布局建模。** 核对 KDA heads 分片、MLA 复制或上下文分片、对象聚合方式与 Store TP；只有原生尺寸和对象组织核对通过后，才能评估整机 SSD 流量。
3. **计算预算有清晰含义。** 初期固定工作点，不用其他 batch 或包含存储等待的端到端 TTFT 反推单 step 时间。要预测真实硬件性能时，再增加对应工作点的标定或按 batch/context 查表的时延模型。
4. **WEKA 是代理工作负载。** Claude Code 的长度/hash/依赖不等于 K3 实际生成的 agent 行为。缺少原文时，无法恢复原始文本在 K3 tokenizer 下的精确长度；必须说明保留的是 trace token 结构，还是重新分词后的结构。
5. **真实尺寸与缩放实验分别标记。** 当前 FEMU 为内存承载的设备，不能仅把容量参数改成 TB 就假定本机可运行。若缩小容量或工作集，需记录缩放规则及局限，不把缩放结果直接当作整机绝对性能。
6. **设备参数要有依据。** 标称 SSD 带宽不能直接换算 NAND 页读时延；正式设备比较需固定几何、并行度、队列、介质时延及工作集，并说明校准来源。
7. **自然淘汰与故障路径分别验证。** 最终磁盘屏障不能无条件要求所有历史对象永远驻留；应区分允许淘汰的对象与要求保留的对象。逻辑删除后的同键重建不以清内存路径代替验收。
8. **失败证据完整保留。** 不放宽现有判据、不挑选单次重跑替换失败结果；分别报告设备、GET、原生入队后 TTFT、HTTP 输出及客户端端到端指标。

## 首份正式报告的验收范围

首份正式报告回答在 K3 真实尺寸缓存和默认布局下，一段真实 agent 会话给单块 SSD 带来哪些 I/O。步骤 4～6 的 tiny 结果用于核验采集工具、缓存生命周期和设备反馈。实施依次经过以下环节。

1. 用已有六次缩放运行校验块事件统计，并在 AIPerf 客体中验证自然淘汰模式。
2. 预检所选真实切片的容量，接入 93 层真实几何和 TP8 分片。保存 rank、对象键、有效字节、checkpoint 及实际存取事件，与步骤 2～3 的规格和分片语义逐项核对。
3. 在同一在线会话与单盘上采集自然产生的读写。记录实际容量、工作集、各 rank 的提交与完成、轮间等待、后台排空和独立重复的波动。运行边界决定对时序、突发和并发的解释范围。
4. 正文呈现读写数量与字节占比、大小分布、时间线、在途深度、LBA 连续性与热点。配置、切片、原始证据和复现命令随报告交付。随后再开展 MLA/KDA 布局对照及 FEMU 内部 GC、写放大实验。

实验矩阵、首份报告图表和各阶段验收条件见 [WEKA 完整回放实施计划](../03-SSD负载与NAND实验/WEKA完整回放实施计划.md)。
