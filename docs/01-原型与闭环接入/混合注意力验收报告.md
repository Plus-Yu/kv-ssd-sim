# 可配置 MLA＋KDA 混合状态验收

本轮补齐了原型的混合缓存功能：原生 vLLM 同时管理 MLA 块和 KDA 状态组，Mooncake 原生 connector 负责查找、传输和磁盘副本，恢复后由原生 scheduler 继续执行。计算仍使用固定时延和确定性占位字节，不执行注意力数学运算。

## 实现

- `configs/hybrid-tiny.json` 配置层顺序、MLA latent/RoPE 维度、KDA heads/head_dim、卷积核及两类状态 dtype。
- MLA 使用原生 `MLAAttentionSpec`，每 token 只存 latent＋RoPE 向量，没有虚构独立的 K/V 张量。
- KDA 的形状和 dtype 来自 vLLM 的 `kda_state_shape` / `kda_state_dtype`。当前 Kimi KDA 上游继承的状态后端枚举是 `GDN_ATTN`，本原型沿用这个原生枚举；并未以 GDN 的尺寸公式替代 KDA。
- KDA 使用原生 `MambaSpec` 的 `align` 模式，包含卷积状态和递归矩阵；内部检查点位置来自 `compute_mamba_prefill_checkpoints`，配置 16-token 导出对齐。只向原生 manager 实际分配的非空列写入检查点。
- 执行 scheduler 返回的 `kv_cache_block_copies`，先复制再更新状态。各混合组共享物理页池，组间按全局 block ID 互斥使用；较小状态使用 page padding。Store 只传输有效内容。
- 显式启用 `prefix_match_unit=64` 和 `store_tp_size=1`，使用原生 `attention_head_major` 与 `mamba_state` 对象格式；如果上游布局降级，初始化直接失败。
- 每个配置有独立对象命名空间。写入和恢复校验完整 SHA256，MLA 和 KDA 两组都必须命中才能恢复混合前缀。

默认 tiny 配置只用于功能验收：

| 项目 | 大小 |
|---|---:|
| MLA 每层每 token | 128 B |
| MLA 每层 64-token 块 | 8192 B |
| KDA 卷积状态 | 3 × 96 × FP16 = 576 B |
| KDA 递归状态 | 2 × 16 × 16 × FP32 = 2048 B |
| KDA 每层完整快照 | 2624 B |
| 共享物理页 | 8192 B |

## 验证结果

命令：`KV_SSD_RUN_NATIVE_TESTS=1 .venv/bin/pytest -q`。本轮 **30 项通过**，日志及对应原生运行产物保存在 `outputs/hybrid-acceptance/`。

| 场景 | 结果 |
|---|---|
| 256-token 整块共享前缀 | 从磁盘恢复 4 个 MLA 对象＋1 个 KDA 快照，256 tokens，所有 SHA256 匹配 |
| 270 / 333-token 非整块输入 | 正确恢复 256-token 边界快照，尾部重新计算，校验通过 |
| 4 层 MLA/KDA、改变 latent 和 head_dim | 每 MLA 对象 20480 B，每 KDA 对象 18688 B，恢复 256 tokens，校验通过 |
| 用 remove 删除 KDA 逻辑对象、保留 MLA | 不发生外部前缀恢复；请求重新计算并生成指定输出长度；最终磁盘耐久屏障报告超时，见下文 |
| 原 dense 路径、子 agent JOIN、多请求 batch | 回归通过 |
| 额度恢复时间判断、JSONL 未写完记录 | 单元测试通过，未向真实会话发送测试消息 |

故障测试没有把耐久性失败伪装成成功：固定的 Mooncake 0.3.14 在本实验中出现 `remove(key)` 后同键重新 PUT 成功、但无法重新确认全部磁盘副本的行为。测试同时断言“scheduler 正确重算”和“最终 disk barrier 明确失败”。当前正常冷恢复只调用 **内存副本驱逐**，保留原磁盘副本，未触发这个问题。涉及对象删除、丢盘恢复的研究需要先解决或隔离该上游行为。

2026-11-16 排查补充：四个被删除后重写的 KDA 键均停留在 MEMORY，新 KDA 键正常落盘。独立普通字节对象也复现：bucket 后端仍认为旧键存在，跳过 offload，master 因而没有新磁盘副本。`remove` 不应描述为物理擦除磁盘数据；定位和证据见 [Mooncake 同键重落盘排查](Mooncake同键重落盘排查.md)。尚未修改 Mooncake 修复该行为。

## 使用

```bash
.venv/bin/python -m kv_ssd_sim replay examples/two_requests.weka.json \
  --output outputs/my-hybrid-run \
  --hybrid-config configs/hybrid-tiny.json --cold-between-turns
```

未传 `--hybrid-config` 时继续使用原 dense 模式。每次使用新输出目录。

## 结论边界

已覆盖单进程、TP=1 的混合对象尺寸、分组、检查点存取、异步磁盘恢复及调度反馈。占位字节只用于检查状态身份和传输一致性，不代表真实 KDA 数值；检查点导出和 CoW 由 CPU 适配器执行，未运行 GPU FlashKDA kernel。本轮端到端用例没有宣称覆盖全部 CoW 触发场景、跨 TP 分片、真实模型精度、推测解码、长时间抢占压力或写放大结论。

vLLM 固定在项目 manifest 中的 `be47189f37f6162991366ff6b91539f6e9d1f432` CPU 版本。后续换版本应重新核对这些内部 API，并重跑原生测试。FEMU 的实际验证另见对应报告，不能把本报告中的普通文件系统恢复当成 NAND 模拟结果。
