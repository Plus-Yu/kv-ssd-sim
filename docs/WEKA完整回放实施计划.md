# Agent 缓存负载下的 SSD 特征研究 · 实施计划与报告大纲

## 研究问题与范围

研究 Claude Code WEKA 会话经 AIPerf、原生 vLLM 调度与 Mooncake 缓存落盘后，一块 FEMU SSD 在什么时候、哪些地址上收到多大的读写，随后考察 MLA/KDA 布局怎样改变这些访问和闪存内部开销。设备承载推理侧缓存。工具执行产生的代码仓库、编译和日志文件 I/O 不在当前输入的观测范围内。

**首份正式报告研究 Kimi K3 真实缓存尺寸下，默认布局和自然缓存策略产生的单盘块 I/O。** 保留 trace 的等待、后台落盘和固定计算预算。TP1 tiny 只用于预实验。布局对照与闪存垃圾回收（GC）放到基线完成之后。请求首 token 时延用于检查回放节奏。

**容量决策。** 已验收的单个 1,536-token checkpoint 样例含 470,605,824 字节唯一对象，约 449 MiB；现有 FEMU namespace 为 384 MiB。这个样例连对象本身就超过盘容量，长会话实际高水位还取决于调度和保留策略。先根据候选切片和预期同时驻留的数据核算 RAM、staging、设备及文件系统空间。优先选择可容纳切片的 FEMU 配置；若本机不足，选择另一段依赖完整的真实会话或使用内存更大的主机。任何容量调整均记录缓存水位与工作集的关系。正式结果使用完整对象的真实字节传输，单 rank 乘八和 tiny 外推仅可用于容量估算。[分片实测](KimiK3-B300步骤3验收报告.md) · [K3 专项计划](KimiK3-B300仿真实施计划.md)

## 主实验口径

| 问题 | 统计口径与对照 |
|---|---|
| 读写有多少、多大？ | 分读写给出操作数、字节、按次数和按字节的占比、I/O 大小分布。Mooncake 逻辑字节和客体块设备字节各自汇总；另列文件系统及未归因流量。 |
| 是否突发，空闲多久？ | 从首个请求发送到后台写入排空划定会话窗口，启动、预填充分开。按固定时间窗统计 IOPS、MiB/s（首版建议 1 秒，突发放大图 100 毫秒）。保留零值，按提交及完成事件求在途请求数，同时标记 think time、对象写出和取回。先核对客体时钟与事件时间基准。 |
| 是否连续，有无热点？ | 以设备提交顺序比较起始 LBA 与上一笔结束位置，注明全流或同方向子流的分母。按固定字节范围统计 LBA 访问频率、重复访问与热点覆盖。块层相邻性描述设备接口的地址顺序。 |
| 为什么出现这些 I/O？ | 逐轮统计 MLA 块和 KDA 快照的创建、落盘、取回及复用间隔。精确归因使用偏移映射；只有时间戳时标明时间关联。对观测结束时尚未再次读取的对象保留截止信息。 |

每次保存源 trace 与切片哈希、实际配置、软件版本、设备初始状态、运行日志、统计脚本与原始表。固定预算的误差和 TCG 速度影响时间轴，按会话和每轮同时给出字节数。若默认配置中所有恢复均命中内存，零设备读进入主结果。另设低内存水位对照，单独标明容量干预。
