# WEKA 完整回放与分析实施计划

记录日期：2026-11-16。

状态更新（2026-11-17）：用户要求先接入 AIPerf，步骤 8 已提前完成第一版 HTTP 接入及小型夹具验收，见 [报告](AIPerf接入验收报告.md)。随后完成 [AIPerf＋FEMU 联合功能验收](AIPerf-FEMU联合验收报告.md)，但含客户端 TTFT 的严格配对未通过，需隔离人工冷缓存准备的计时干扰。真实完整 trace 仍未完成，其余步骤按下列顺序推进。

目标按三个阶段推进：**真实切片出结果 → 完整 trace 稳定回放 → 布局对照研究**。现有原生 vLLM、Mooncake 和 FEMU 功能闭环作为基础，不重复搭建环境。

| 3 | 验证自然缓存生命周期：关闭强制冷缓存，测试并发保存、内存淘汰、磁盘恢复、缺失重算 | 容量压力下确实产生 SSD 回读；恢复校验通过；请求依赖及并发语义保持正确 | 待实施 |

## 顺序调整规则

1. **步骤 1 决定 AIPerf 是否提前。** 若目标 trace 大量依赖当前不支持的嵌套语义，将步骤 8 提前到步骤 5 之前，并据此调整步骤 7 的实现范围，避免重复建设两套完整回放器。否则先用现有驱动完成语义完整的切片。
2. **步骤 3 是当前关键验证。** 已有 FEMU 实验通过主动清缓存强制 SSD 恢复；下一步要确认自然请求与容量压力下也会正确回读。正式并发实验不启用 `--cold-between-turns`，该参数保留为功能验收工具。
3. **步骤 4 可与输入审计独立推进。** 同键问题不阻止分析 trace；但实验涉及删除重建时，必须完成对应修复验证，或清楚限定实验不覆盖该路径。工作可独立推进不表示启动多个代理。
4. **步骤 6 后再优化布局。** 先确认工作负载产生足够 SSD 访问，避免内存命中或软件开销掩盖布局差异。
5. 运行成本由切片测量确定，暂不承诺完整文件所需时间。现有占位数据预准备有 512 MiB 上限，步骤 1、5 要检查其影响。

## 第一版报告要回答的问题

- 多少请求复用了前缀，多少 token 需要重新计算？命中统计分别来自哪一层缓存？
- 哪些请求等待 SSD，等待时间多长？对应 TTFT 和请求完成时延如何分布？
- MLA 与 KDA 各产生多少对象、多少逻辑读写字节？
- 设备实际读写量与对象逻辑读写量相差多少？此阶段称为 **I/O 字节比**，不直接称为 NAND 写放大。
- 仅改变 SSD 读时延时，请求时延如何变化？哪些变化可归因于存储等待，哪些属于原型或 TCG 开销？

每次运行保存输入及配置、版本和源码标识、对象事件、设备事件、请求指标及校验结果。失败运行保留并单独标记，不混入成功统计。单次对照只作功能和趋势探索，不宣称统计显著性或真实 GPU 性能。
