## Mooncake 删除后同键重新落盘

状态：2026-11-16 已定位并独立复现，尚未修复。master 删除逻辑对象后，SSD bucket 后端仍判断旧键存在，跳过再次 offload；新内存副本因而没有对应的已注册磁盘副本。详见 [排查报告](Mooncake同键重落盘排查.md)。后续修复需协调删除、索引与对象代际，避免同键改值时复用旧磁盘内容。

## AIPerf v0.13.0 请求驱动

状态：2026-11-17 已按用户要求提前完成第一版 HTTP 接入，见 [验收报告](AIPerf接入验收报告.md)。AIPerf＋FEMU 联合功能链路也已验证，见 [联合报告](AIPerf-FEMU联合验收报告.md)。真实 tokenizer、完整 trace 和所有 DAG 变体仍待推进。

联合验收未通过项：含客户端 TTFT 的严格慢读配对失败。GET 与原生 TTFT 增加约 414 ms，但人工冷缓存导致入队前阶段减少约 498 ms，端到端 TTFT 反向。需将冷缓存准备与被测请求发送分离、保留原始计时，再进行配对和重复实验；不得以单次重跑替换失败证据。正式自然淘汰实验应关闭该人工清缓存流程。

目标：用 AIPerf 的 WEKA loader、会话 DAG、并发、SPAWN/JOIN 和发送节奏替代自写请求回放部分。保留现有直接提交 Request 的小型模式作为回归入口。

需要补齐：

1. 兼容的 HTTP / 流式输出服务端接口；输出进度必须由真实调度、模拟计算和真实恢复完成事件决定。
2. 固定 tokenizer 和模板，核对实际 token 长度及共享前缀，不能把文本重建后的请求未经检查地视为原 trace。
3. 核对 AIPerf 的因果/固定时间模式与当前选项的差异；不能直接假定同名选项语义一致。
4. 分开记录客户端端到端时延、服务端排队、模拟计算和存储恢复时间。
5. AIPerf 只替换请求生成与发送层，不替代模型执行器、KV 数据或引擎循环。

参考：[AIPerf v0.13.0 WEKA 回放文档](https://docs.nvidia.com/aiperf/v0.13.0/tutorials/datasets-inputs/replay-weka-agentic-coding-traces)。
